# Архитектура ProjectHub

Документ с проектными решениями, обоснованиями и описанием ключевых механизмов. Актуален для версии **0.4.0+**.

---

## 1. Общие решения

### Почему Next.js 16 + App Router

Проект использует Next.js 16 с App Router по нескольким причинам. Во-первых, монорепозиторий frontend + backend упрощает деплой — не нужен отдельный API-сервер. Во-вторых, Route Handlers (`app/api/`) обеспечивают server-side логику с прямым доступом к Prisma без дополнительного слоя. В-третьих, React Server Components используются минимально — основной UI является client-side (`'use client'`), что упрощает работу с Zustand и интерактивными компонентами (DnD, файловые загрузки).

Standalone output (`output: "standalone"` в `next.config.ts`) позволяет деплоить собранное приложение без `node_modules` — только `server.js` + минимальный набор зависимостей. Это критично для VPS с ограниченным диском (~10 ГБ).

### Почему SQLite + Prisma

SQLite выбран как база данных исходя из ограничений сервера: один VPS с 10 ГБ диска не позволяет комфортно разворачивать PostgreSQL или MySQL. SQLite работает с файлом на диске, не требует отдельного процесса и демонстрирует отличную производительность для нагрузки в один-два десятка пользователей.

Prisma ORM обеспечивает типобезопасный доступ к данным, автоматическую генерацию миграций и удобный синтаксис для сложных запросов (включая рекурсивные включения `include` для деревьев). `prisma db push --accept-data-loss` используется вместо полноценных миграций — это допустимо для прототипа, где схема может меняться между релизами.

### Почему Zustand (а не Redux / React Query)

Единственный Zustand-стор (`src/lib/store.ts`) хранит всё состояние приложения: проекты, узлы, текущего пользователя, состояния раскрытия. Выбран по причинам: минимальный boilerplate, нет обёрток-провайдеров, простая типизация через TypeScript интерфейс. React Query не используется — вместо этого применяется паттерн «загрузить всё → мутация → перезагрузить всё». Для текущего масштаба данных это оправдано.

## 2. Авторизация и доступ

### NextAuth v4 + Credentials Provider

Используется классический Credentials Provider (username + пароль). JWT-стратегия сессий (не database sessions) — это упрощает масштабирование и не требует отдельного хранилища сессий. В JWT-токен вкладываются `id` и `role` пользователя через коллбэки `jwt()` и `session()`.

### Turbopack standalone — баг с JWT-полями

При использовании Turbopack standalone-режима кастомные поля JWT теряются при передаче с сервера на клиент. Обходной путь: endpoint `/api/me` выполняет прямой запрос в БД по `session.user.name` и возвращает `{id, username, role}`. Клиент вызывает `api.getMe()` вместо чтения из `useSession()`. Важно: `useSession()` нельзя вызывать вне `SessionProvider` (например, на странице `/settings`).

### Хеширование паролей

`src/lib/auth.ts` — `scryptSync` с 16-байтной случайной солью. Формат хранения: `salt:derivedKey` (hex). Это встроенный модуль Node.js, не требует дополнительных зависимостей. scrypt выбран как более ресурсоёмкий по сравнению с простым SHA — значительно увеличивает стоимость брутфорса.

### Middleware и защита маршрутов

`src/middleware.ts` использует `withAuth()` из `next-auth/middleware`. Matcher исключает `/login`, `/register`, `/api/*`, статику и фавиконку. Все остальные маршруты требуют авторизации — неавторизованный пользователь перенаправляется на `/login`.

### Ролевая модель

Две роли: `admin` и `user`. Первый зарегистрированный пользователь всегда получает `admin`. Разделение прав:

| Право | admin | user |
|---|:---:|:---:|
| Видеть все проекты | ✅ | — |
| Настройки системы (`/settings`) | ✅ | — |
| Управление регистрацией | ✅ | — |
| CRUD своих проектов | ✅ | ✅ |
| CRUD узлов внутри своих проектов | ✅ | ✅ |
| Загрузка файлов | ✅ | ✅ |
| Экспорт протоколов | ✅ | ✅ |

### Изоляция данных

Проекты привязаны к пользователю через `Project.userId`. API-эндпоинт `/api/all-data` фильтрует проекты: `where: isAdmin ? {} : { userId }`. Узлы наследуют изоляцию через `projectId` — если пользователь не имеет доступа к проекту, он не получит его узлы.

## 3. Дерево узлов

### Типы узлов

Модель `Node` использует `nodeType` для определения типа узла. Поддерживаются четыре типа:

| Тип | Описание | Дочерние узлы | Специфические поля |
|---|---|---|---|
| `branch` | Контейнер-ветка | Да | `branchType` (визуальная категория) |
| `item` | Листовой элемент с динамическими полями | Нет | `fields` (произвольные ключ-значение) |
| `task` | Задача с чекбоксом выполнения | Нет | `completed`, `taskTypeId` |
| `protocol` | Протокол с описанием и таблицей решений | Нет | `protocolText`, `decisions[]` |

### Самоссылающаяся модель

`parentId` (FK → `Node.id`) для организации древовидной структуры. `branchType` — визуальный тег ветки для категоризации.

```
Project
├── Branch (branchType: "tasks")
│   ├── Task (completed: true, taskTypeId: "...")
│   ├── Protocol (protocolText: "...", decisions: [...])
│   └── Item (fields: {url: "...", port: 443})
└── Branch (branchType: "credentials")
    └── Item (fields: {login: "admin", password: "..."})
```

### Динамические поля

Поле `fields` хранится как JSON-строка в SQLite (`String @default("{}")`). На клиенте это `Record<string, unknown>` — пользователь может создавать произвольные пары ключ-значение через `NodeDetailPane`. Нет жёсткой схемы, нет предопределённого набора полей.

### Протоколы

Протокол (`nodeType: "protocol"`) — отдельный тип сущности с двумя специфическими полями в `fields`:
- `protocolText` — текстовое описание протокола (string)
- `decisions` — массив решений, каждый объект содержит: `task`, `deadline`, `responsible`, `comment`

При создании протокола в название автоматически подставляется текущая дата в формате `DD.MM.YYYY`. В панели редактирования отображаются textarea для текста и интерактивная таблица решений с возможностью добавления/удаления строк.

### Рекурсивная загрузка

API загружает деревья узлов с помощью цепочки `include` глубиной 5 уровней в Prisma. Функция `parseNodeFields()` рекурсивно обходит дерево и парсит JSON-поля из строк в объекты.

## 4. Drag-and-Drop

### @dnd-kit/core

Выбран `@dnd-kit/core` v6 как современная, accessible-ориентированная библиотека для DnD. `@dnd-kit/sortable` установлен, но пока не используется — текущий DnD реализует только перемещение между ветками, а не сортировку внутри одного уровня.

### Механизм

1. Каждый `NodeRow` обёрнут в `useDraggable` — drag-ручка (`GripVertical`) появляется при наведении.
2. Ветки (`nodeType === 'branch'`) дополнительно обёрнуты в `useDroppable` — при перетаскивании над веткой появляется подсветка (`ring-2 ring-primary/50`).
3. Рефы объединены через коллбэк (`mergedRef`) — один элемент является одновременно и источником, и целью.
4. `PointerSensor` с `activationConstraint: { distance: 5 }` предотвращает случайное перетаскивание при клике.
5. При `dragEnd` выполняются проверки: целевой узел — ветка? Не является ли перетаскиваемый узел предком цели? Не является ли уже дочерним? При успешной проверке вызывается `updateNode(id, { parentId })`.

## 5. Файловые вложения

### Загрузка (`POST /api/upload`)

1. Пользователь перетаскивает файл в drop-зону или выбирает через `<input type="file" multiple>`.
2. Клиент отправляет `POST /api/upload` с `FormData` (поля: `file`, `nodeId`).
3. Сервер проверяет: авторизацию, существование узла, права доступа к проекту, размер файла (лимит 50 МБ).
4. Файл сохраняется на диск: `uploads/{timestamp}-{random}.{ext}`.
5. Создаётся запись `FileAttachment` в БД с метаданными (имя, оригинальное имя, MIME-тип, размер).

### Скачивание (`GET /api/files/[id]`)

Файлы **не отдаются статически** — каждый запрос проходит через API с проверкой существования записи в БД. Возвращается бинарное содержимое с заголовками `Content-Type` и `Content-Disposition` для корректного отображения имени файла.

### Удаление (`DELETE /api/files/[id]`)

Проверяется авторизация и права доступа к проекту. Файл удаляется с диска (`fs.unlink`) и запись удаляется из БД (каскадно через Prisma).

## 6. Дублирование узлов

`POST /api/nodes/[id]/duplicate` выполняет рекурсивное глубокое копирование: исходный узел и все его потомки клонируются с новым `id` и суффиксом `(копия)` в имени. Клон создаётся на том же уровне, что и оригинал (тот же `parentId`). Файлы вложения **не копируются** — только структура дерева и поля.

## 7. Экспорт

### Экспорт ветки в таблицу

`GET /api/nodes/[id]/export` рекурсивно собирает все дочерние элементы типа `item` (включая вложенные в подветки) и формирует плоскую таблицу. Столбцы — это объединение всех ключей из `fields` всех элементов. Строки — значения полей каждого элемента. Клиентская функция `openExportTable()` генерирует HTML с таблицей и открывает в новом окне.

### Экспорт протокола (для Outlook)

Кнопка «Экспорт» в панели протокола генерирует HTML, оптимизированный для копирования в письмо Outlook. Ключевые решения:

- **Inline-стили** — Outlook не поддерживает `<style>` в теле письма, все стили задаются через `style="..."` атрибуты
- **Нет `@media print`** — форматирование не для печати, а для вставки в письмо
- **Чистый белый фон** — без теней, карточек, скруглённых углов
- **Таблица с границами** — `border-collapse:collapse` с явными `border-bottom` и `border-right` на ячейках, чтобы границы сохранились при вставке
- **`white-space:nowrap`** на колонках «Срок» и «Ответственный» — предотвращает переносы в узких столбцах
- **Шрифт Segoe UI** — стандартный шрифт Outlook, обеспечивает максимальную совместимость
- **Без контейнера-обёртки** — минимальная вложенность DOM для чистого копипаста

Формат вывода: заголовок (название протокола) → дата → описание (если есть) → таблица решений.

## 8. Плавающие кнопки действий

В панели редактирования (`NodeDetailPane`) над областью прокрутки располагается sticky-панель с кнопками действий. Это позволяет сохранить или экспортировать данные, не прокручивая к нижней части формы.

- **Кнопка «Сохранить»** — появляется только при наличии несохранённых изменений (detected via JSON-сравнение snapshot'а текущего состояния с состоянием на момент открытия). Анимация: плавное появление/скрытие через `opacity` + `scale` transition.
- **Кнопка «Экспорт»** — всегда видна для веток (экспорт в таблицу) и протоколов (экспорт в формат для Outlook). Для элементов и задач не отображается.

Реализация: при открытии узла в `useRef` сохраняется JSON-строка snapshot'а (name, branchType, fields). При каждом рендере текущее состояние сериализуется и сравнивается с snapshot'ом. После успешного сохранения snapshot обновляется.

## 9. Системные настройки

Модель `SystemSetting` — простой key-value store (`key` — первичный ключ, `value` — строка). Текущие настройки:

| Ключ | Значение по умолчанию | Описание |
|---|---|---|
| `max_file_size_mb` | `10` | Максимальный размер загружаемого файла в МБ |
| `allow_registration` | `true` | Разрешена ли самостоятельная регистрация |

Настройки создаются при регистрации первого (admin) пользователя через `/api/register` или при вызове `/api/seed`. Админ может менять их через `/settings`.

## 10. Деплой

### Host-build стратегия

На VPS с 10 ГБ диска Docker-сборка Next.js-приложения не помещается (образ может занимать 2-3 ГБ). Поэтому применяется host-build:

1. `bun install` — установка зависимостей на хосте
2. `bun run build` — сборка Next.js в standalone-режиме
3. Копирование артефактов в `.next/standalone/`
4. Запуск `node .next/standalone/server.js` через systemd

### Reverse proxy

Caddy проксирует внешний порт на localhost:3000. Конфигурация зависит от инфраструктуры.
